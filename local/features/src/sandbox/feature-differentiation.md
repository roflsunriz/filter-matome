# 公式watchバンドルから見た機能差別化調査

## 調査目的

ニコニコ動画公式watchページの公開JavaScriptを、ログイン済みChromeからraw CDPで取得し、filter-matomeが公式機能と同じ領域で競合している部分と、NicoCache_nl連携によって独自価値を出せる部分を分ける。

この調査は公式コードの再利用を目的としない。確認したのはアセット構成、機能語、参照先、既存filter-matomeの責務との差だけであり、公式JavaScriptをimport、eval、または製品コードへコピーしていない。

## 調査条件

- 実施日: 2026-07-24 JST
- 対象: `https://www.nicovideo.jp/watch/sm9`
- Chrome: `150.0.7871.130`
- CDP: `http://127.0.0.1:9222` のWebSocketへ直接接続
- 最終capture: `official-watch-bundle/captures/2026-07-23T20-04-22-782Z/`
- 取得範囲: `resource.video.nimg.jp/web/scripts/nvpc_next/assets/` のJavaScript
- 取得量: 82ファイル、2,943,681 bytes
- manifest SHA-256: `B6F5E2F350BA23B77A6D4B316B8627FC7E408C29DDE49FDD0B0543C65786A18D`
- 保存していないもの: HTML、Cookie、Authorization、全ヘッダー、DOM、スクリーンショット

初回captureでは、NicoCache_nlが `www.nicovideo.jp/local/` として注入したスクリプトを検出した。最終captureは公式watchアセットCDNだけに限定し、filter-matome自身を公式機能として数えないようにした。

動的確認用の一時BrowserContextでは、CDPの `Network.setBlockedURLs` によりHTTP、HTTPS、WebSocket、FTPを遮断した。外部`fetch`の失敗、Cookie 0件、local/session storageが空または利用不能であることを実測した。機能集計自体はさらに安全側に倒し、取得したJavaScriptを実行せず、ローカルファイルの静的文字列走査だけで行った。

## 差別化の評価

| filter-matomeの領域 | 公式ベースラインとの関係 | 差別化評価 | 維持・強化すべき価値 |
| --- | --- | --- | --- |
| ローカルキャッシュ再生と削除済み・視聴不能動画への継続導線 | 公式はオンライン配信と権利・会員状態を正本にする。NicoCache_nlのローカル資産管理はcapture内に現れない。 | 最重要 | 公式watchページの複製ではなく、「手元にある正当なキャッシュを安定して見られる継続性」を中心にする。キャッシュ状態、再生可否、復旧理由を明確に表示する。 |
| スタンドアロンvideo-playerでのコメント取得・描画・投稿 | 公式にも再生とコメント投稿があるが、ローカルキャッシュ上で両者を統合する点が異なる。 | 高い | 公式API契約への最小接続、ローカル動画との時刻同期、投稿失敗理由、公式ページへ戻る復旧導線を磨く。公式UIの完全コピーは狙わない。 |
| comment-filter2の非表示・置換・コマンド制御・大量ルール最適化 | 公式コメント機能は強いが、ユーザー定義の変換、正規表現診断、JSON/CSV/JSONL移行、Worker処理はfilter-matome固有。 | 最重要 | 「見え方を自分で制御できる」「ルールの効果と負荷を説明できる」を前面に出す。公式のニコる・コメント表示と競合せず、その入力を高度に整形する層として位置づける。 |
| mylist2の全マイリスト横断検索、メモ、入出力、Google Driveバックアップ | 公式マイリスト・あとで見る・シリーズは強い。単なる追加・一覧は差別化になりにくい。 | 高い | 複数リスト横断検索、ユーザー所有のメモ、明示的なデータ移送、削除済み動画やローカルキャッシュ状態の保持に集中する。 |
| watch-historyの再生実測、完了率、統計、視聴ログ、条件削除、シリーズ常駐通知 | 公式にも視聴履歴はあるが、ローカル再生を含む詳細な進捗・統計・データ管理は別の価値軸。 | 高い | 「公式とローカルをまたぐ個人分析」「ブラウザーを閉じても動くシリーズ通知」「バックアップと復旧」を強化する。 |
| movie-infoの複数情報源比較とRaw JSON | 公式UIは視聴体験を優先し、NicoCache_nl固有のMediaInfoやキャッシュ状態は扱わない。 | 中から高 | 一般視聴UIではなく、障害診断、キャッシュ確認、API差分調査の開発者・上級者向けツールとして明確にする。 |
| mlinkの背景、原宿風表示、マトリックス背景、細粒度操作 | 公式プレイヤーにも再生操作とレスポンシブUIがある。装飾だけでは更新追従コストに負けやすい。 | 補助的 | カスタマイズは残しつつ、キャッシュ操作、コメント調査、関連ツールへの統合パネルという実用価値を主軸にする。 |
| フォロー、いいね、共有、推薦、広告・プレミアム導線 | 公式のサービス・収益・アカウント基盤と密結合している。 | 追随非推奨 | 同等実装を増やさず、公式UIを尊重して必要な場所へ安全に橋渡しする。 |

## 研究から得た方針

1. filter-matomeの中心価値は「公式の代替UI」ではなく、`ローカル継続性 × 個人データ所有 × 高度なコメント制御` とする。
2. 公式が強い再生、マイリスト、フォロー、共有、推薦は、同等機能を増やすより壊れにくい統合境界を維持する。
3. 新機能の優先度は、ローカルキャッシュでしか成立しないか、ユーザーがデータを持ち出せるか、公式UIでは得られない診断・変換能力があるかで判断する。
4. 公式DOMやハッシュ付きクラスへの依存を減らし、URL、`HTMLMediaElement`、公開API契約、NicoCache_nlの `/cache/*` を責務ごとに使い分ける。
5. 公式バンドル調査は更新追従の証拠取得に限定し、コピーした内部実装を製品へ持ち込まない。差別化文書には識別子、アセット名、API契約、観測日だけを残す。

## 次に検証する候補

- 同じ手順で、ログアウト状態、プレミアム状態、コメント投稿禁止動画、チャンネル動画のアセット差をmanifest単位で比較する。
- watchページで実際に操作した後に追加ロードされる遅延アセットを、操作名と対応づけて別captureにする。
- capture間でアセットURL、SHA-256、機能シグナルを比較する差分コマンドを追加し、公式更新で影響しそうな統合境界だけを通知する。
- filter-matomeの各機能について「公式同等」「公式補助」「NicoCache_nl固有」のラベルをREADMEに付け、新規実装の判断基準にする。

## 制約

- 1動画、1アカウント状態、1回の初期ロードだけを対象にしている。
- 文字列の存在は機能の実装・有効化を証明せず、不在も別の遅延バンドルに機能がないことを証明しない。
- A/Bテスト、地域、会員種別、動画種別、操作後の遅延ロードでアセット構成は変わり得る。
- 公式サービス全体の機能比較ではなく、watchページ初期ロードと現行filter-matomeの差を研究した結果である。
